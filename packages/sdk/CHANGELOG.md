# @centrifuge/sdk

## 3.0.0

### Major Changes

- The deployed protocol stack is now version `"3.2"`, the name the indexer already stores on every pool, and `"3.1"` is no longer a protocol version. `protocolContext()` resolves pools to `protocolVersion: "3.2"`. `getDeployment`, `parseEventLogs({ protocolVersion })` and `protocolContext` throw `UnknownProtocolVersionError` when given `"3.1"`. Pass `"3.2"` instead. Contract addresses are unchanged; for the changes to the exported `ABI` object see the next entry.
  
  Breaking for code that reads `ProtocolContracts` (the type of `protocolContext()` results): `poolEscrowFactory` and `oracleValuation` are now optional, absent on v3.3 and on chains whose address book excludes the OracleValuation respectively, and `escrowFactory` (v3.3 only) is added. Code that reads either field as a `HexString` must handle `undefined`.
- Every protocol ABI in the exported `ABI` object now comes from the contract registry instead of hand-written signatures, which changes its types. Breaking: `ABI.OnchainPM` no longer has `trustedCall(address,bytes)` and `ABI.ScriptHelpers` no longer has `fromBytes32`; `ABI.OnOffRampManagerFactory` is the `OnOffRampFactory` ABI and no longer carries the legacy factory's `DeployOnOfframpManager` event (`parseEventLogs` still decodes it); `DeployOnchainPM` on `ABI.OnchainPMFactory` names the deployed address `onchainPM` instead of `manager`. Also changed: `OnchainPM.execute` is `payable`, and `ABI.ScriptHelpers.toBytes32` is overloaded for `uint256` and `address`. Calldata and event decoding are unchanged. `ABI.Currency`, `ABI.ERC6909` and `ABI.Multicall` are unchanged.
- Breaking: on a pool under a hub policy, an awaited write that ends in `OutOfPolicy` resolves with that status and no hash instead of being sent, so a caller that treats resolution as success records a write that was never signed; check `result.type`. `OperationStatus` also has a new member, `OperationOutOfPolicyStatus`, which a `switch` over `status.type` that must be exhaustive has to handle.
  
  A hub transaction for a pool under a v3.3 hub policy is checked before it is signed. Each inner call is asked of the pool's `StdHubPolicy` for the connected wallet's address; when any call is not ready, the transaction ends with a terminal `OutOfPolicy` status (`{ id, type: 'OutOfPolicy', title, calls }`): this hub transaction is not signed or sent, a send the method made before it stays done, and a wallet on another chain has already been asked to switch chain. It does not reject; a failed read of the check rejects with `HubPolicyPreflightError`. A method that sends more than once stops at the first `OutOfPolicy`: no claim notification follows a refused approve, issue or revoke, no later network of `deployToNetworks` starts, and `pool.setAdapters` on v3.3 judges every network before it signs the first. A sequence that signs a send which is not a hub call first (an on/off-ramp's accounting token registration, a ramp deploy) cannot stop earlier, and that send stays done. Writes prepared in backend mode are not checked by the SDK.
  
  `calls` lists only the calls that are not ready, in order, each with its `data`, `functionName`, decoded `args` (a refund address is `args.refund`), `delay`, `validAfter`, `expiresAt` (set only for `expired`) and a `status` of `needs-authorization`, `pending`, `expired`, `undetermined` (matured, expiry unknown) or `forbidden`. A `forbidden` call carries a `reason`: `callerNotAllowed` (the policy confines the signer away from the call), `accountingOnly` (under onchain accounting, an accounting call from anyone but the NAVManager, a snapshot hook other than the NAVManager, or a share price update from anyone but the SimplePriceManager) or `other`. A delay of zero, or a matured authorization within its expiry, is ready and sends unchanged. The verdicts are read from the hub chain when the transaction starts, and so is the installed policy. The policy's `expiry` is read only for a delayed call whose authorization has matured, from the contract and, for a policy with no `expiry()` view, from the indexer (`public-api` target only): an indexer outage fails that case alone, never an instant call or a call that is not ready for another reason. A pool without a policy, a v3.2 pool, a simulation and `buildOnly` send the request they sent without the check; `Centrifuge.batchTransactions` judges the batch as one before its single send. `pool.initiateAuthorizations` is not checked, since no policy classifies scheduling.
  
  `PoolAuthorization` gains `scheduledAt`, the block time of the scheduling log in unix seconds as a `bigint`, so an operator can plan the execution; a row without a valid `createdAt` throws `AuthorizationFoldError`. `pool.refreshHubPolicyReads()` clears the cached results of `hubExecutionPolicy()` and `authorizations()` and of the two indexer queries behind them, and makes a running subscription of either fetch again; `centrifuge.clearQueryCache` alone does not. New exports: `OperationOutOfPolicyStatus`, `OutOfPolicyCall`, `OutOfPolicyCallStatus`, `OutOfPolicyForbiddenReason` and `HubPolicyPreflightError`.
- `pool.updateOracleValuationFeeder` checks the client's address book before anything is signed. When the target is the hub chain's registry OracleValuation, or the book lists none on that chain, the book must record for it the ABI digest of the OracleValuation ABI the SDK encodes with; otherwise the call throws `DeployedContractVersionError`. A provided book may put the OracleValuation at any address that carries that digest. With the bundled book every address is refused on Plume, Avalanche, BNB, HyperEVM, Monad, Pharos and Arc, where the book excludes the OracleValuation; Arc was accepted before. Breaking: `DeployedContractVersionError` no longer has `deployedVersion`; it carries `address`, `bookDigest` and `buildDigest` (`address` and `bookDigest` are `null` when the book has no address or ABI record), and its message names them. A v3.3 pool's escrow is now read from `EscrowFactory`.

### Minor Changes

- The protocol ABIs now come from the bundled `@centrifuge/addressbook` release (7.0.0-sha-0a732dd) instead of a generated copy. The ABIs the SDK encodes and decodes with are byte-identical, so `ABI`, calldata and event decoding are unchanged, and so is the bundled book. A book passed through the `addressBook` option is now digest-checked against every ABI that release publishes, not only the ones the SDK used to bundle. A book whose address for a contract the SDK never calls (a `TokenFactory`, say) carries a digest other than that release's is now refused with `AddressBookAbiMismatchError`. A book built from the bundled book's heads is accepted as before, now without the warning that listed ABI names the SDK had no ABI for.
- `poolNetwork.deploy()` on a v3.3 pool, to a spoke on another chain than its hub where the spoke's `AdapterFailover` is not yet the pool's adapter manager, now also makes it that manager (`Hub.updateManager`, kind `adapter`) and names the address the spoke's `ProtocolGuardian.safe()` returns its steward (`Hub.managerCall`), so the pool's adapters there can be replaced if they stop delivering. The SDK only refuses a zero `safe()`, with `AdapterFailoverStewardMissingError`, before anything is sent. Where `AdapterFailover` already is the manager, its stewards are left as they are; a spoke on the hub's chain and v3.2 pools build the same calls as before. In backend mode `deployVaults()` lists both calls among those its `deployVault` action cannot carry. `ProtocolContracts` gains the optional `adapterFailover`.
- The bundled address book is `@centrifuge/addressbook` 7.0.0-sha-d7cf88c. Testnet migration calls (`migrationPlan`, `migrationPreCheck`, `migrationStep`) now go to the V33Migration facade `0x3AF8225b934091B08689b4144b07F92B04C6bf86` on Sepolia, Base Sepolia, Arbitrum Sepolia and HyperEVM testnet, instead of the retired `0x0ea29238…`. Its ABI adds `multicall((bytes,uint256)[])`, which no SDK call uses yet. Mainnet's book now carries v3.3.0 stacks and three new chains (Robinhood Chain, Linea, ADI); the SDK still serves only v3.2 on mainnet, so mainnet resolution is unchanged and those three chains, which have no v3.2 stack, are not listed. A mainnet pool cannot resolve to protocol 3.3, since mainnet serves only 3.2. `Pool.updateOracleValuationFeeder`, the one call that runs the deployed-version check, would refuse 3.3 on mainnet with `DeployedContractVersionError`, which now carries `served: false` and names the unserved version as the reason; other calls do not run this check.
- Catalog validation proves token approvals exact. `checkApprovalExactness` flags an ERC-20 or ERC-6909 `approve` unless a later action calls the spender with the same amount reference, so no allowance outlives the script; an infinite allowance, or a spender or amount that is not a single pinned value, is always flagged. `validateCatalogWorkflow` applies it to every reachable template. Templates that set `guards.allowance` keep the runtime allowance check and are exempt, and use-only fragments (templates declaring `param` variables) are checked in their callers. `CatalogTemplate` gains the optional `guards` flags, and `ApprovalTemplate` is exported. Both pinned catalogs pass unchanged.
- A balance sheet can read and submit what its spoke has queued for the hub. Every deposit, withdrawal, issue and revoke only queues its delta on the spoke, on v3.2 and v3.3, and the hub's holding amount and share count move only when the queue is submitted. `balanceSheet.queued(assetIds)` returns, per asset, the queued deposits and withdrawals, and the net share delta with `isPositive`; it reads `SnapshotQueue` on v3.3 and `BalanceSheet` on v3.2, and refreshes on the queue's events. `balanceSheet.submitQueued(assetIds)` sends every asset with a queued delta, then the share delta, in one multicall signed by a balance-sheet manager, paying one message fee each; it skips repeated assets and refuses an empty submit. Deposit, withdraw, issue and revoke are unchanged. `ProtocolContracts` gains `snapshotQueue`.
- `PoolAuthorization` has `canceledAt` (unix seconds as a `bigint`, the block time of the cancel log rounded down) and `canceledTxHash` (the cancel transaction). Both come from the log that canceled the run and are `null` unless the item is `canceled`. A cancel log without a parseable timestamp throws `AuthorizationFoldError`, as a consumption log already does for `executedAt`.
- `shareClass.directIssuancesInFlight()` lists the direct issues and revokes the hub sent to a remote `ShareManager` that the spoke has not executed (a failed message is listed, a cleared one is not), from the new `shareManagerCalls` catalogue entry on public-api; it fails on `graphqlTarget: 'api-v3'`, which never had the rows. `DirectIssuanceInFlight` is exported.
- `pool.executeAuthorizations(datas)` executes a matured group of hub calls on a v3.3 pool: the calldata that was scheduled goes to the Hub unchanged, in one transaction (a `Hub.multicall` when it has several calls), and every call is judged by the pool's policy before anything is signed. Pass the `data` of the items that share a `txHash` in the order `pool.authorizations()` lists them. The instant calls the group depends on are rebuilt through the entity code that sends them today, refunded to the signer: a `notifySharePrice` per notified network after each `updateSharePrice`, a `notifyPool` before the first call of a deployment to a network the pool is not on yet (where the group holds a `notifyShareClass`, `setRequestManager` or a deploying `updateVault` for it), and a `notifyAssetPrice` before each `updateVault` that deploys a vault. A link or unlink has no instant call. `setAdapters` calls are sent first, each in a transaction of its own, and the rest is priced against the adapters they install. The cross-chain fee is derived from the messages the owning entity declares for each call. A call that is not ready (`pending`, `expired`, `undetermined`, `needs-authorization` or `forbidden`) ends the transaction in `OutOfPolicy` with nothing signed. Before anything is read, an empty group, repeated calldata, a `multicall` wrapper, a selector the v3.3 Hub does not carry, a call for another pool, a function no SDK entity builds, a `managerCall` with a local value and extra gas on a function whose messages carry none are refused with an `Error`. A v3.2 pool then throws `UnsupportedForProtocolVersionError` (on mainnet too), and after that a `managerCall` to the `BatchRequestManager` of a kind no entity builds is refused before anything is signed. A group with a `setAdapters` call is several transactions: built or batched, it is refused before anything is read.
  
  `pool.authorizations()` lists one item per scheduling run, so calldata scheduled again after a cancel or a consumption is a new item and the earlier run stays in the list. `PoolAuthorization` has a `runId` (`<txHash>:<logIndex>` of the scheduling log), which keys a table row, since the runs of one calldata share an `authId`. `executedAt` (unix seconds as a `bigint`) and `executedTxHash` come from the consuming log and are `null` unless the item is `consumed`. A cancel or consumption with no run open before it is counted in `skipped` once per row, as `schedulingRowMissing`, and so is a scheduling row whose id already has a run open, as `endingRowMissing`: the first run stays the open run.
- `shareClass.holders()` and the v3.3 migration pre-check's holder read list investors only on the `public-api` target. The indexer now writes positions for every holder, escrows and vaults included, and marks each with `holderKind`; the SDK asks for `INVESTOR` positions, so the lists match the earlier ones. Against an indexer that does not publish `holderKind`, the read fails rather than listing protocol holders.
- A v3.3 pool's hub policy and its authorizations can be read and acted on. `pool.hubExecutionPolicy()` returns the installed policy with its parameters, or `null` for a v3.2 pool, no policy or a cleared one. A parameter the indexer did not publish stays `null`, a latest install whose log carried no address returns `address: null`, and `expiry` is read from the policy contract only when the indexer has none. `pool.authorizations()` returns `{ items, skipped }`: one item per scheduling run (calldata scheduled again after a cancel or a consumption is a new item, and `authId` is shared by every run of it) with its Hub function name, its decoded `args` (a refund address is `args.refund`), `validAfter`, `expiresAt` and a status of `scheduled`, `matured`, `expired`, `undetermined` (past `validAfter` with no known expiry), `canceled`, `consumed` or `orphaned` (a later policy install made it unreachable); it is an empty list on a v3.2 pool. Both reads refresh on the indexer poll and exist only on the `public-api` GraphQL target. `pool.initiateAuthorizations(datas)` schedules one authorization per hub call (one `Hub.multicall` for several, the plain call for one) and `pool.cancelAuthorization(data)` cancels one; both refuse a v3.2 pool with `UnsupportedForProtocolVersionError`. A matured group is executed with `pool.executeAuthorizations`, and one call by running its owning action again with the same inputs; a call that carries a refund address only matches when run with the same one. New exports: `HubExecutionPolicy`, `PoolAuthorization`, `PoolAuthorizationList`, `SkippedAuthorization`, `AuthorizationStatus` and `AuthorizationFoldError`.
- `centrifuge.adapters(centrifugeId)` returns `hyperlaneAdapter`, and `ProtocolContracts` gains the optional `hyperlaneAdapter`. It is the Hyperlane adapter of the v3.3 stack, the address the MultiAdapter's adapter sets hold (the address book's `hyperlaneAdapter`, not `hyperlaneStandby`), and `undefined` on chains without it, which today is every v3.2 chain and all of mainnet.
- A write on a pool that is migrating from v3.2 to v3.3 is judged by the migration gate before it builds. The gate reads the pool's migration once, finds the spoke the write targets (the asset's chain for order settlement, the named network for a vault, member or manager write, both ends for a cross-chain share transfer, the hub for pool configuration and the share price) and refuses what that spoke's phase does not allow with a `PoolMigratingError` whose new `gate` field names the action, the spoke, the phase, the verdict, the reason and the actions the phase still allows. A refused write never resolves addresses, asks for a signature or pays for a message. Pools that are not migrating pass after one indexer read; a data source that cannot answer passes with a warning, since the chain remains the final gate. New exported types: `MigrationGateRefusal` and `MigrationGateTarget`.
- A migration plan bundle now holds at most 90% of the smaller of the hub's block and the per-transaction cap, divided by a 1.3x gas pad: 11,614,995 on Ethereum. A full bundle declared with the pad stays under EIP-7825's 2^24 cap, which Ethereum enforces. `GAS_LIMIT_PAD_PERCENT` (130n) and `MAX_TRANSACTION_GAS` are exported. `pool.migrationStep(operation, options?)` and `pool.migrationBundle(operations, options?)` take `MigrationSendOptions`, exported, whose `gas` is the gas limit the transaction declares; without it the wallet estimates, and batching and `buildOnly` ignore it.
- `pool.migrationBundle(operations)` sends hub migration operations as one transaction through the facade's `multicall`, with each entry's relays priced at signing and `msg.value` their sum. Entries are simulated in order before signing, and a failing one is refused with `MigrationSimulationError`, which now carries the entry's `position` in the bundle. Its `operation` reads `'multicall'` when every entry passes alone and only the bundle fails.
- `pool.migrationClaimables(centrifugeId)` lists what investors can still claim on one spoke's v3.2 request manager, per vault and investor: an executed deposit's shares and a redeem payout, with `refusedByHook` when the share token's hook refuses the claim and `gaps` where the investor set may be short. It reads without running the whole pre-check, and answers nothing to claim once the pool runs on v3.3. The pre-check's `spoke.claimables` rows read the same figures and are unchanged.
- `migrationGasLimit(simulated)` returns the gas limit a migration transaction declares: the simulated gas with `GAS_LIMIT_PAD_PERCENT`, held at `MAX_TRANSACTION_GAS` only when the simulated gas itself fits under it. A call that simulates over the cap is declared above it, since EIP-8037 (Glamsterdam, live on Sepolia) draws state gas above the per-transaction cap.
- `pool.migrationInputs(centrifugeId)` and `pool.migrationHubInputs(spokeCentrifugeIds)` derive the inputs of the v3.2 to v3.3 migration steps from the live v3.2 stack at one block, the indexer naming candidates and the chain deciding every list.
- The SDK carries the v3.2 to v3.3 migration module. `pool.migration()` reads a pool's migration from public-api: the hub phase, every spoke with its phase, freeze generation, relayed steps and where each landed, and the per-spoke gate state P1 to P6 the allowed-actions table keys on. `pool.migrationStep(operation)` signs one manager-side facade operation on the chain it belongs to after simulating it; `pool.pinMigrationRecord(record)` pins the unsigned record; `pool.migrationDrainWorklist(centrifugeId)` lists the open orders a spoke still has to drain. `PoolMigratingError` now carries `gate` when the local build refused a write on a migrating pool: the action, the spoke it keyed on, the phase, the verdict, the reason and the actions that phase still allows.
  
  Consumer contract: apps read `protocolVersion` and `status` for display only and never branch on version. The SDK alone resolves addresses, ABIs and transaction semantics per pool, and refuses a write the pool's migration phase does not allow on the spoke it targets. An app shows the `PoolMigratingError` it gets back; it does not predict the phase.
- `pool.migrationPlan()` derives the migration's remaining operator calls from the phases the pool holds, each simulated on the chain that signs it, sliced where the destination refuses the whole and grouped into the approvals a signer makes; `pool.migrationNextAction()` names the first of them or the wait in flight. Entries carry the operation `migrationStep` signs and the relay's quoted value.
- Every `pool.migrationPreCheck()` row and note carries a stable `code` (`PreCheckCode`, listed in `PRECHECK_CODES`), one per kind, so an app picks its text by code instead of matching the subject or message. The spoke claimable rows name their vault, investor and field, and the hub admin rows and notes their address, in `refs` (`PreCheckRefs`). Messages and subjects are unchanged.
- `pool.migrationPreCheck()` reports every row of Protocol's pre-check with its severity, step, chain, source and amount, `blockingRows` naming what holds a step; `pool.migrationGuards()` and `pool.migrationLanding()` run the live guards before a plan entry is signed and say where its relayed steps landed; `pool.migrationSettleReport()` classifies a remote spoke's parked messages and finds the retries that land, which `pool.migrationSettle()` signs, along with the post-activate VaultRouter bridger grant.
- `pool.migrationRampIds(centrifugeId)` lists every ramp accounting id a spoke's v3.3 ramps need, a receipt and a liability id per ramp asset, each with its asset, its token id and whether the spoke registry already knows it. It reads the same calls the plan's ramp registrations read, after the offboard as before it; the plan still offers a registration only for the ids not registered.
- A pool's first activation on a network no longer waits for its adapters to arrive. On v3.2, `poolNetwork.deploy` sends `setAdapters` at the head of the Hub batch, in one transaction, and builds it. On v3.3, where `Hub.setAdapters` reverts inside a Hub batch, it sends `setAdapters` and then the Hub batch in one EIP-5792 `wallet_sendCalls` prompt, or as two transactions when the wallet does not support it; building it still refuses. The pool messages are priced against the LayerZero adapter being installed, and `BuiltTransaction` gains the optional `pendingPoolAdapters` naming it per destination, so whoever signs a built activation prices it the same way. On v3.3, the `wallet_sendCalls` path reports the first transaction as pending as soon as the wallet names it, and stops waiting when the transaction is cancelled. `pool.deployToNetworks` batches all networks into one transaction on v3.2. `deploy` no longer emits `AwaitingCrosschainDelivery`; the status type stays exported.
  
  New `centrifuge.layerZeroDeliveries(fromCentrifugeId, toCentrifugeId, txHash)` reports where each LayerZero message of a transaction stands on the destination (`delivered`, `inFlight`, `stuck`, `skipped`), and `centrifuge.retryLayerZeroDelivery(fromCentrifugeId, toCentrifugeId, txHash)` re-executes the `stuck` ones, such as pool messages that arrived before the pool's adapters and reverted with `InvalidAdapter()`.
- Pool-scoped adapter reads, and `pool.setAdapters` refuses adapters of another protocol version. On a chain that hosts v3.2 and v3.3, `centrifuge.globalAdapters(hub, target)` and `centrifuge.adapters(centrifugeId)` answer the newest version. A pool now reads its own version with three calls. `pool.globalAdapters(centrifugeId)` returns the global (pool 0) set and threshold on its version's hub MultiAdapter: the local adapters it may use toward a network. `pool.remoteGlobalAdapters(centrifugeId)` returns the same set on that network's MultiAdapter toward the hub: the remote addresses, which can differ from the hub's. `pool.deployedAdapters(centrifugeId)` returns the adapter addresses the registry lists for its version, to name them. `pool.setAdapters` checks each adapter on its own chain, local adapters on the hub and remote ones on the target: first its code, then its `entrypoint()`. It throws the new `AdapterVersionMismatchError` before signing when the entrypoint is not the pool's MultiAdapter there, because such an adapter reverts every pool message with `NotEntrypoint`. The error lists every refused adapter in `mismatches`, each with a `reason` (`noCode`, `noEntrypoint`, `otherVersion`, `unknownEntrypoint`). The check now reads every target network, so `setAdapters` needs a client for each one, and throws `ProtocolVersionResolutionError` for a target where the pool's version is not deployed. A failed RPC read is thrown as it is. New exported types: `AdapterMismatch` and `AdapterMismatchReason`.
- A client given an `addressBook: { book }` whose ABI digests on its `environment` differ from the ABIs built into the SDK release now throws `AddressBookAbiMismatchError` on its first resolution, before any request, listing each address and both digests. The address of every registry key the SDK encodes calls with is compared with that key's ABI, whatever ABI name the book records, and refused when the book has no ABI record for it. `allowUnsafeMainnet` does not bypass it. To fix it, drop the option to use the bundled book, or build the book from the registry heads the bundled book pins. A provided book also logs one `console.warn` per client listing the ABI names, under keys the SDK encodes no calls with, that it has no generated ABI for; that is expected and needs no action. The bundled book is not checked.
  
  New public surface for running against another address book:
  
  - `Config.addressBook?: { book: AddressBook; allowUnsafeMainnet?: boolean }`, the file `build-book` writes. On mainnet the constructor throws `UnsafeMainnetAddressBookError` (new export, carrying `bookId` and `bundledBookId`) for a book other than the bundled one unless `allowUnsafeMainnet` is `true`.
  - `centrifuge.addressBookId()`, the `bookId` of the book the client resolves against.
  - `centrifuge.registryHeads()`, the registry head each network of that book is pinned to.
- The 2.10.0 allowlist exports are back, deprecated, so code written against 2.10.0 keeps compiling and running: `KNOWN_DEPLOYMENTS`, `KnownDeployment`, `DeploymentMismatchError`, `IndexerDeployment`, `IndexerDeploymentResponse` and `VerifyOptions`. The SDK reads none of them: protocol addresses come from the client's address book, never from the indexer, and nothing throws `DeploymentMismatchError`. `KNOWN_DEPLOYMENTS` lists the bundled address book's v3.2 mainnet stacks in the 2.10.0 shape, keyed by `centrifugeId`, built on first access and read-only. Use `centrifuge.protocolContext(centrifugeId)`, or the registry from `await centrifuge._addressBook()`, instead.
- `pool.scheduleOutOfPolicy(status)` schedules an action that a v3.3 pool's hub policy delayed, from the `OutOfPolicy` status it ended in, as one group. It sends one transaction on the hub chain: an `initiateAuthorization` for each call that needs an authorization, and the independent instant calls with their cross-chain fees, in the order of the batch. A `Freeze` with `Member` updates sends the Freeze and schedules each Member; a share price beyond the guard schedules `updateSharePrice` alone. The calls it schedules share a `txHash` in `pool.authorizations()`, which is the group `pool.executeAuthorizations` takes once they matured.
  
  The `OutOfPolicy` status gains `batch`: every judged call in the order it would be sent, each `{ data, status, deferred }`, where `status` is `ready` or the status of a call that is not ready (`calls` is unchanged and lists only those). `deferred` is true for a ready call that executing the group rebuilds: a `notifySharePrice` after a share price update that is not ready, a `notifyPool` before a deployment that is not ready, and a `notifyAssetPrice` before a vault deployment that is not ready. Scheduling does not send them. The status of `wrapTransaction`, `sendCallsInOrder`, the up-front check of `pool.setAdapters` and `centrifuge.batchTransactions` all carry it. New export: `OutOfPolicyBatchCall`.
  
  Before anything is signed, `scheduleOutOfPolicy` throws for a status of another pool, a `forbidden`, `pending`, `expired` or `undetermined` call (it names the call and what to do), a status with no call that needs an authorization, a ready `setAdapters` (the Hub refuses it inside a batch), a ready deployment leg for a network whose `notifyPool` the batch leaves to the execution, a `deferred` that is not what the rules give for the batch and a call whose messages cannot be derived; a v3.2 pool throws `UnsupportedForProtocolVersionError`. `pool.initiateAuthorizations` stays for calldata held without a status.
  
  `pool.executeAuthorizations` does not send the investors' claim notifications that follow an issue or a revoke: on v3.3 they are `BatchRequestManager` calls and cannot share its transaction. `pool.hasClaimsAfterExecution(datas)` says from the calldata whether a group has any, and `pool.claimsAfterExecution(datas)` sends them in one transaction right after the Execute confirms. Investors and claim counts come from the indexer, which it waits for (every 3 seconds, for up to 2 minutes) until the epochs the group issued or revoked show as closed; it then notifies the investors the indexer lists as unclaimed, each for the number of their unclaimed closed epochs. It throws, with nothing signed, when the indexer has not caught up or every investor is already claimed, when the group has no issue or revoke (before anything is read), and, on a v3.2 pool, `UnsupportedForProtocolVersionError`.
- `PoolNetwork.deploy`, `deployShareClasses` and `deployVaults` read whether the pool is wired to a network from the indexer's pool adapter rows for both directions: the spoke must mirror the hub's live set with nothing in flight. Re-running a deployment after delivery skips `setAdapters`. The hub's set is the authority: a configuration the destination is still receiving is not sent again, and a hub set other than the LayerZero 1/1 the SDK configures is never overwritten; the deployment stops instead. `OperationAwaitingCrosschainDeliveryStatus.hash` is optional: absent when the messages were sent by an earlier transaction.
- `poolNetwork.shareManagerStatus()` names the network's `ShareManager` and whether its balance sheet grant is live (`isBalancesheetManager`) or in transit (`crosschainInProgress`), read from the network's protocol context and `pool.balanceSheetManagerStatus()`; `null` where the network has no `ShareManager`, which is every v3.2 network. `ShareManagerStatus` is exported.
- Address book 8: the testnet `V33Migration` facade is the redeployed contract `0x25f4dA38…` (registry head `bafkreicj6…`, a patch layer over v3.3.0), which emits `EscrowKeySeeded` and `ShareQueueSeeded`. The facade `0x3AF8225b…` is retired: a pool armed on it can no longer be continued through the SDK.
- An investor can bridge shares on a v3.3 pool. `shareClass.crosschainTransferShares` now sends a signer that is not a bridger of the pool through `TokenBridge.send`: it approves the share token to `TokenBridge` when the allowance is short, then sends with the destination's EVM chain id and the message fee as value, priced with the gas limits `TokenBridge` keeps for the share class (`MessageV3_3` gains an optional `extraGasLimit`). A bridger keeps the direct `Spoke` call. A destination the source's `TokenBridge` does not map throws `InvalidBridgeChainError`, and a pool that has not made the source chain's `TokenBridge` a bridger throws `BridgeNotEnabledError`, both before anything is approved. The bridger route now approves the share token to `Spoke` when the allowance is short; without it, `Spoke`'s `transferFrom` reverted every direct v3.3 bridge. The TokenBridge route cannot be batched, and `buildOnly` builds it only when no approve is needed.
  
  A transfer the pool's bridge circuit breaker would refuse on the hub is now refused before signing with `BridgeLimitError`, whose `reason` is `paused`, `limitUnset`, `exceedsRateMax` or `exceedsWindow`. A hook that is not the address book's breaker cannot be judged, so the transfer goes ahead with a warning. A transfer a hub manager authorized for its exact route, sender, receiver and amount passes. Before this check, a transfer from a remote spoke burned the shares and then failed on the hub. `shareClass.bridgeLimit(originCentrifugeId)` returns the hub's state: no hook, an unknown hook, or the breaker with `paused`, `rateMax`, `rateWindow`, `used`, `windowStart` and `remaining`.
  
  `pool.isAllowed(action, centrifugeId, { destinationCentrifugeId? })` answers whether the pool's migration allows an action on one chain. It uses the same derivation as the migration gate, including the hub chain without a spoke row. The answer is `{ allowed: true }` or the refusal `PoolMigratingError.gate` would carry, with `code: 'POOL_MIGRATING'`; it is read afresh each time and does not update. The gate table is exported: `isAllowed`, `isBridgeAllowed`, `isActionAllowed`, `MIGRATION_ACTION` and `SPOKE_GATE_STATE`, and the types `SpokeGateState`, `MigrationAction`, `GateAnswer`, `GateVerdict`, `GateOptions`, `NamedActionOptions`, `BridgeSource` and `BridgeDestination`. Other new exported types: `MigrationGateAnswer`, `BridgeLimit` and `BridgeLimitReason`. `ProtocolContracts` gains the optional `bridgeCircuitBreaker` and `circuitBreakerGuard`.

### Patch Changes

- `pool.deployToNetworks` with two or more networks that it sends as one batch (a v3.2 pool, or a v3.3 pool whose networks are all wired) no longer ends with `You provided an invalid object where a stream was expected` after the batch was signed and sent. It streams the batch's statuses and completes, and a pool with a hub policy gets its `OutOfPolicy` status instead of that error. Networks that run one at a time were not affected.
- A fee estimate made only of v3.3 messages is priced on the sending chain's v3.3 stack. While a pool migrates its own context still resolves to v3.2, so the migration plan and the arm's signature failed with "exists on protocol v3.3 only, but is priced for 3.2".
- The migration gate reads the facade on the pool's hub chain before the indexer: a pool with no facade or a `hubPhase` of None passes without an indexer read, an activated pool passes once every spoke's max reserves are restored, and a migrating pool is judged on a fresh `pool.migration()` read with no cache. A state that cannot be read (the hub facade, a spoke facade, the indexer) now refuses the write with `PoolMigratingError` naming the read, an action the gate table does not map is refused on a migrating pool, and a settlement toward a spoke whose offboard relay is on the hub chain but not in the indexer yet is refused naming the relay. `pool.isAllowed` answers the same way.
- `pool.migrationPlan()` holds the first `relayOffboard` toward any spoke until every other armed spoke reads Frozen at the hub's current freeze generation, and names the chain and the case in the stop: its Freeze is in flight, it was never frozen, it reads Armed again after an Abort, an Abort or re-freeze toward it is in flight, or its Arm is in flight. An offboard that has started finishes its slices, and a spoke already offboarded does not hold it.
- A lane install entry concerns the spoke whose lane it is on both halves, so `pool.migrationNextAction()` puts both on that spoke's page, a half that fails in simulation stops that spoke alone, the skip for an installed half names the spoke, the arm goes ahead for the other spokes without it while the hub onboard waits until every spoke is armed and the activate stops on one never armed, the spoke half is not offered once the hub half stopped, and the entry's spoke phase is the spoke's own.
- The spoke side of a migration lane builds `installPoolAdapters(poolId, hub)`. It passed the spoke itself, so the plan failed right after the start on any pool with a remote spoke.
- `pool.migrationGuards(plan, index, { sentWith })` takes the indexes of the earlier entries in the same send and reads them as going first for the previous-entry check. A plan bundle with consecutive slices toward one spoke can then be signed: before, its second slice failed on the first one reading pending. A slice signed on its own still waits for the one before it to land.
- From a spoke's freeze on, the migration inputs put back what the walk removed from the v3.2 stack, read from the facade's records: the removed managers and the ramps among them, the rotated assets, the frozen classes and sync keys, and the hook grants on the hook each token had before rotation. `pool.migrationPlan()` then offers only the offboard and spoke onboard items the facade has not recorded as done, and keeps the finalize totals whole-spoke. Restored lists read `record` in the inventory's `sources`, and `notCarried` names the live v3.2 managers an offboard did not remove.
- `pool.migrationStep` and `pool.migrationBundle` price the hub onboard's relays: one `ManagerCallFromHub` toward each remote armed spoke, read from the hub facade's `armedSpokes`. Before, the hub onboard was sent with no relay fee and the Gateway reverted with `NotEnoughGas()` whenever the pool had a spoke on another chain.
- `pool.migrationPreCheck()` reports each row's `amount` in the decimals of the token it counts: an investor order, a liability holding and a spoke claimable in its asset's or share token's decimals, an ERC-6909 escrow balance in its token id's decimals, and `null` when the token does not answer. A 1,000 USDC pending deposit now reads 1,000 instead of 1,000,000,000. The unclaimed round counts (`maxDepositClaims`, `maxRedeemClaims`) carry no `amount`, and now show when they are not zero.
- `pool.migrationPreCheck()` reads the hub and every spoke side by side and batches the per-asset escrow reads (share token owner, decimals, rotation) into one multicall per chain, so a three-chain testnet pool's pre-check takes 6 to 9 seconds instead of 20 to 29. The report is unchanged: the same rows, notes and order.
- The migration plan, the pre-check and `pool.migration()` read one spoke set, `pool.migrationSpokeCandidates()`: the chain directory united with the v3.2 hub's spoke record and the migration's own spokes, each confirmed on its chain. A chain that cannot be read in five seconds is named `unreadable` instead of counted inactive: `pool.migrationPlan()` lists it under `unreadableSpokes`, holds the arm while the hub is Armed and stops the hub onboard on it, naming the chain; the pre-check names it as a stop on the arm. A live spoke that was never armed now appears in `pool.migration().spokes` with no phase and no steps while the hub is Armed or HubOnboarded. The migration gate judges such a spoke P1 while the hub is Armed, so spoke configuration there is refused until it is armed.
- The migration pre-check and inputs read `VaultRegistry.vaultDetails` as the struct the contract returns. They crashed on any pool with vaults ("object is not iterable").
- A migration plan stop caused by a protocol error names it with its arguments, such as `EpochsNotSynced(…)`, instead of printing the raw revert data.
- `shareClass.updateSharePrice()` takes an optional `skipNetworks` (a list of `centrifugeId`s) so the caller can leave networks out of the price notification, for example while a bridge to one of them is paused. The SDK still decides where the share class is deployed and only subtracts the skipped networks; an id the share class is not deployed on is ignored, and skipping every deployed network is a hub-only update.
- The hand-defined `pharos` chain now names the canonical Multicall3 address, so viem batches reads on Pharos the way it already does on every other chain. Until now every read went out as its own `eth_call`, which tripped the rate limit on the default `rpc.pharos.xyz` endpoint and multiplied request counts on metered providers.
- `pool.migrationPlan()` plans nothing on a pool that is already on v3.3, whose migration row reads activated, or whose migration contract no longer holds it while the row is past none: the plan is complete and empty, its one skip says which of the three it is, and `pool.migrationNextAction()` is `null`. A version the transport cannot resolve no longer fails the plan: with no migration row, the v3.3 hub registry decides whether the pool was created on v3.3 (held there, and not reserved by the migration contract). `pool.protocolVersion()` refuses a transport that projects no version, or a pool the catalogue does not list, with `ProtocolVersionResolutionError`.
- `pool.migrationPlan()` stops a spoke's offboard and onboard while a step of that phase relayed toward it since its last Freeze is still in flight, in the indexer or as a hub `StepRelayed` of the last 5,000 blocks the indexer has not written yet, instead of deriving the same step again from the unchanged spoke; the freeze stops on a parked Abort only. A step unmatched to a gateway message is a warning, not a stop, and `pool.migrationGuards` refuses an entry whose step is in flight, or whose spoke has a hub relay the indexer has not written yet (the same sweep), while noting an unmatched one. `options.ignoreStepsInFlight`, on the plan and on the guards, turns the in-flight stop into a warning or an informational row; a parked step still stops. A hub RPC that refuses the sweep stops that spoke instead of failing the plan.
- The migration pre-check declares `ShareToken.hook()` in its ABI. It failed on every pool at the holder memberships ("[GAP] v3.2 ShareToken.hook: the read failed").
- `pool.migrationPreCheck()` answers a terminal report on a pool already on v3.3 (migration activated, or created on 3.3) instead of throwing `UnsupportedForProtocolVersionError` while resolving the v3.2 contracts. The report comes from the migration row and follows it as the indexer catches up; its armed spokes are the row's spokes past None.
- `pool.migrationPreCheck()` reads every spoke the v3.2 hub's record names, not only the pool's active spokes. A spoke only that record names, whose v3.2 pool is not live, no longer holds the hub onboard; one that is live still does. A spoke the pre-check cannot read now says why ("not read: …") instead of "no client configured for its chain".
- A spoke read that fails stops only that spoke's migration pre-check report, with a `stop` row on the arm naming the read and its error; the other chains still report. An indexer candidate read that answers something other than a list is refused by name instead of failing as a raw `TypeError`.
- `PRODUCTION_BUDGETS.seedGas` is now `640_000n` (was `560_000n`), matching Protocol's production migration budgets. The seed step now emits one event per escrow key. The other 15 budgets are unchanged.
- Two readers of one indexer query with different post-processing no longer share a cached shape. The migration inputs read took `allVaults` rows raw while `ShareClass` mapped them, so after the migration pages loaded, the Orders page of a migrating pool failed with `Cannot read properties of undefined (reading 'toString')`. The same held for `merkleProofManagers`, `onOffRampManagers`, `onOffRampRelayers` and `offRampAddresses`.
- `centrifuge.repayBatch()` sends `Gateway.repay` to the Gateway on the source chain that holds the underpaid batch, whatever protocol version it belongs to: every version deployed there is read for `underpaid`, and the repayment goes to the one holding it, priced by that version's MultiAdapter. It throws a `RepayBatchError` before signing, naming the batch hash: `reason: 'not-underpaid'` when no Gateway holds the batch, `'ambiguous'` when more than one does or the holding Gateway is shared by versions with different MultiAdapters, and `'no-refund-address'` when it is built with `buildOnly` without a `fromAddress`, whose refund would go to the zero address.
- `centrifuge.retryMessage()` sends `Gateway.retry` to the Gateway on the destination chain that holds the failed message, whatever protocol version it belongs to: every version deployed there is read for `failedMessages`, and the retry goes to the one holding it. It throws before signing, naming the message hash, when no Gateway holds the message or more than one does.
- `contractAbis.Root` is on the v3.2 and v3.3 ABI sets, so `Root.endorsed(address)` can be read through `protocolContext` without parsing an ABI.
- `pool.migrationSettleReport` no longer refuses a pool whose hub sent the spoke v3.2 traffic before the migration: executed payloads before the Arm that the v3.3 message table cannot split are skipped. One after the Arm still raises the `[GAP]`.
- A direct revoke to a remote spoke on v3.3 carries the extra gas `ShareManager` needs (`SHARE_REVOKE_EXTRA_GAS`, 300,000) in the hub call and in the value the hub transaction pays, so the relayed message executes on the spoke. `emptyMessageV3_3` prices a `ManagerCallFromHub` that carries an extra gas limit. An issue, and a revoke on the hub chain, carry 0.
- `protocolContext({ poolId, centrifugeId })` resolves v3.2 for a spoke of a v3.3 pool while the spoke's migration phase is before `Onboarded`, and re-emits v3.3 once it onboards. The hub chain keeps the pool's version. A v3.3 spoke context whose first migration read fails errors with `ProtocolVersionResolutionError` instead of resolving v3.3; a failed later poll keeps the last answer and retries. `pool.setAdapters`, `pool.remoteGlobalAdapters` and `pool.deployedAdapters` resolve the remote network at the hub's version, so a spoke that has not onboarded yet takes and answers its v3.3 adapters.
- `pool.migrationStep` simulates a step with the relay fee it then sends. It simulated with the operation's value alone, so every step that sends a cross-chain message (arm, freeze, offboard, onboard, activate) failed before signing with the Gateway's `NotEnoughGas()`. A simulation revert the SDK could not decode, such as `0xdd629f86`, is named from the protocol's errors (`NotEnoughGas()`) on `MigrationSimulationError`.
- A migration step whose batch the hub Gateway holds underpaid reads `underpaid` (`MigrationStepLanding`, `MigrationStepCounts.underpaid`, `EntryLandingState`) instead of `inFlight`: the plan stops the spoke on it with a reason naming `centrifuge.repayBatch`, `ignoreStepsInFlight` does not plan past it, the guards refuse the next entry toward the spoke, and it is left out of the steps in flight the next action reports. `crosschainMessageRows` carries each message's `payloadStatus`.
- `centrifuge.workflowMarketplace()` reads the centrifuge/workflows catalog from release `cfe52fa` by default, on mainnet and testnet. It adds the workflows of the pools created since the last pin (HYB, deHYB, CFGS, SISF, JQQQ, zSMB, RWAt) and follows the v3.3 migration addresses (deJAAA, deJTRSY, ACRDX), so workflows already whitelisted against those addresses carry a new version and script hash and must be re-approved before the policy can change.
